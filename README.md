
# CRM Sales

تطبيق عربي لإدارة عمل مندوب المبيعات: العملاء، الزيارات، نتائج الزيارة، المواعيد والاتفاقيات. الواجهة React/Vite، والخادم Node.js، والبيانات محفوظة في SQLite على جهاز تشغيل الخادم.

## التشغيل الكامل على Windows

المتطلبات: **Node.js 24 LTS** وGit. لا يتطلب هذا المسار Docker أو Java أو Android Studio أو حساب Supabase.

افتح PowerShell في مجلد المشروع:

```powershell
npm install --include=dev
npm run dev
```

الأمر الثاني يشغّل الواجهة والباك اند معًا. افتح عنوان الواجهة الذي يظهر في الطرفية، عادةً **http://127.0.0.1:5173**. إذا كان المنفذ مشغولًا سيختار Vite المنفذ التالي ويطبعه. اترك الطرفية مفتوحة؛ `Ctrl+C` يوقف الخادمين.

في أول تشغيل، اضغط **إنشاء حساب** وأدخل اسمك وبريدك وكلمة مرور لا تقل عن 8 أحرف. هذا ينشئ حسابًا حقيقيًا في قاعدة البيانات المحلية. حسابات مشروع Supabase القديم لا تنتقل تلقائيًا إلى قاعدة البيانات الجديدة. لا توجد كلمة مرور افتراضية أو حساب مشترك مخفي.

بعد الدخول، ابدأ الدوام ثم أضف عميلًا وابدأ زيارة. أكمل الزيارة بنتيجة، أو موعد، أو متابعة، أو اتفاقية موقعة. راقب صفحة المزامنة لتأكيد أن التغييرات وصلت إلى الخادم.

### تحديث نسخة موجودة

```powershell
git status
git pull --ff-only
npm install --include=dev
npm run dev
```

إذا أوقف Git التحديث بسبب تغييرات محلية، احتفظ بها قبل دمج التحديث؛ لا تستخدم `git reset --hard`. لا حاجة إلى ملفات patch منفصلة.

## التحقق من الخادم وقاعدة البيانات

أثناء تشغيل التطبيق، افتح طرفية ثانية في المشروع:

```powershell
npm run health
```

هذا يطلب `GET /api/health` ويتحقق من تنفيذ استعلام على قاعدة البيانات. النتيجة السليمة:

```json
{ "status": "ok", "database": "ok" }
```

لا يكفي فحص الصحة وحده لإثبات عمل تسجيل الدخول وحفظ البيانات. لتشغيل اختبارات المصادقة وعزل المستخدمين واستمرار البيانات، ثم بناء الواجهة:

```powershell
npm run check
```

تعمل الاختبارات على قواعد مؤقتة منفصلة ولا تمس بياناتك. يوجد أيضًا اختبار رحلة المتصفح، موضح في `docs/verification.md`.

## مكان البيانات والإعدادات

ينشئ الخادم `data/crmsales.sqlite` تلقائيًا. قاعدة البيانات وملفات الجلسات المحلية ليست ضمن Git. تبقى الحسابات والبيانات بعد إيقاف البرنامج وإعادة تشغيله. عند نقل التطبيق إلى جهاز آخر، انقل نسخة احتياطية من قاعدة البيانات أيضًا. لإجراء نسخة ملف بسيطة، أوقف الخادم أولًا ثم انسخ مجلد `data` كاملًا.

لا تحتاج إلى إعداد `.env.local` للتشغيل الافتراضي. عند الحاجة انسخ `.env.example` إلى `.env.local` وعدّل القيم:

| المتغير | الافتراضي | الاستخدام |
| --- | --- | --- |
| `API_PORT` | `3001` | منفذ الخادم أثناء `npm run dev` |
| `VITE_PORT` | `5173` | أول منفذ يحاول Vite استخدامه |
| `VITE_API_BASE_URL` | `/api` | مسار API من الواجهة؛ احتفظ به للتشغيل المحلي |
| `DATABASE_PATH` | `./data/crmsales.sqlite` | ملف قاعدة البيانات |
| `PORT` | `3001` | منفذ `npm start` |
| `HOST` | `127.0.0.1` | عنوان الاستماع؛ الجهاز المحلي افتراضيًا |

المتغيرات القديمة `VITE_SUPABASE_PROJECT_ID` و`VITE_SUPABASE_ANON_KEY` لم تعد مطلوبة لمسار التشغيل المحلي. لا تضع مفاتيح خادم سرية في متغيرات تبدأ بـ`VITE_`، لأنها تصل إلى المتصفح.

## تشغيل النسخة المبنية

```powershell
npm run build
npm start
```

افتح **http://127.0.0.1:3001**. يقدّم خادم واحد الواجهة المبنية وواجهات API، دون الحاجة إلى Vite أثناء التشغيل. يجب إيقاف جلسة `npm run dev` أولًا أو تغيير المنفذ. هذا إعداد محلي؛ نشره للعامة يتطلب HTTPS وتخزينًا دائمًا ونسخًا احتياطية وضبط التسجيل وفق سياسة الجهة المستخدمة.

## إنشاء حساب من الطرفية أو استعادة كلمة المرور المحلية

يمكن للمسؤول عن الجهاز إنشاء مستخدم من الطرفية:

```powershell
npm run user:create -- --email person@example.com --name "اسم المستخدم"
```

تُطلب كلمة المرور محليًا. لإعادة ضبط حساب موجود في **هذه القاعدة المحلية**، أضف `--reset`. يعطّل ذلك جلساته القديمة. إرسال رسائل استعادة كلمة المرور بالبريد ليس مهيأ في الوضع المحلي، ولذلك لا يعرض التطبيق رسالة إرسال وهمية.

## ما الذي تغيّر عن النسخة الأصلية؟

- أُزيل عنوان Supabase القديم من مسار تسجيل الدخول النشط. فشل DNS السابق كان فشل اتصال، وليس دليلًا على خطأ كلمة المرور.
- أصبح `npm run dev` يشغّل الخادم والواجهة وقاعدة البيانات من أمر واحد.
- أضيفت مصادقة حقيقية، كلمات مرور مشتقة بـ`scrypt`، جلسات قابلة للإلغاء، وحماية بيانات كل حساب على الخادم.
- تستخدم الشاشات المتصلة بيانات المستخدم الفعلية. الصفحات التجريبية القديمة باقية في المصدر للمراجعة، لكنها ليست مسار الاستخدام الجديد.
- لا تعتبر المزامنة ناجحة حتى يقر الخادم بحفظ السجل. تبقى الطلبات الفاشلة ظاهرة لإعادة المحاولة.

ملفات `supabase/functions/server` محفوظة كمسار تاريخي؛ لا يشغّلها الأمر المحلي ولا يحذف بيانات أي مشروع Supabase. لا توجد عملية ترحيل تلقائية من ذلك المشروع. يستمر هذا التطبيق كمساحة بيانات مستقلة لكل مستخدم؛ مشاركة فرق العمل، صلاحيات المدير، إرسال البريد/SMS واستضافة خرائط تفاعلية تتطلب إعدادًا وتطويرًا إضافيين، ولا تُعرض كأنها وظائف مكتملة.
